Scope: what to teach, in what order, which misconceptions to target, and which exercise types work, for a "teach first, then practice" platform. Learner = rusty adult re-learner; target = fluent hand-written Python and PostgreSQL up to US big-tech interview level.

## Q1. Python novices & re-learners: documented misconceptions, notional machines, code tracing — and how to teach them with predict-the-output / tracing exercises

### Takeaway
The strongest and most consistent CS-ed finding here is that novices' errors come from a faulty *notional machine* (their model of what the computer does when code runs), so the notional machine should be an explicit learning objective, taught via memory/frame diagrams (Python Tutor style) and practiced with read/trace/predict items *before* and alongside writing items. Python-specific trouble spots cluster around references vs. copies (aliasing), assignment semantics, if/elif vs sequential ifs, return vs print, scope/frames, and a handful of Python "gotchas" that the official docs themselves call out (shared mutable defaults, list aliasing, mutating while iterating, floor division).

### Cited Findings

**Notional machines (theory)**
- [R] Sorva (2013) argues the literature treats notional machines as a major obstacle in intro programming and recommends instructors make the notional machine an *explicit learning objective*; also suggests multiple notional machines at different abstraction levels may help. Juha Sorva, "Notional Machines and Introductory Programming Education," ACM TOCE 13(2), 2013, 8:1–8:31, DOI 10.1145/2483710.2483713 (older, 2013; verified) — [Crossref](https://api.crossref.org/works/10.1145%2F2483710.2483713); [dblp](https://dblp.org/rec/journals/jeric/Sorva13)
- [R] Later work notes Sorva's point that students may hold multiple, possibly contradictory mental models of a notional machine at once — [arXiv 2606.12427 (2026), "Planning on Paper"](https://arxiv.org/pdf/2606.12427)
- [R] Sorva's 2012 doctoral thesis ("Visual Program Simulation in Introductory Programming Education", Aalto University) contains an appendix cataloguing ~160 documented novice misconceptions from the literature, and proposes *visual program simulation* — the learner (not the tool) steps through execution by manipulating a memory diagram (older, 2012; not re-verified) — [Aalto handle](https://aaltodoc.aalto.fi/handle/123456789/3534)
- [R] Sorva, Karavirta & Malmi (2013) review of generic program-visualization systems for intro programming, ACM TOCE 13(4), DOI 10.1145/2490822 (older; not re-verified) — conclusion consistent with Hundhausen (see Q2): engagement level matters more than the visuals.

**Python Tutor**
- [R] Philip Guo, "Online Python Tutor: Embeddable Web-Based Program Visualization for CS Education," SIGCSE 2013, DOI 10.1145/2445196.2445368 (older, 2013; not re-verified) — the tool renders stack frames and heap objects with arrows, which directly visualizes the "names refer to objects" model. Tool: [pythontutor.com](https://pythontutor.com)

**Tracing first / read-before-write**
- [R] Xie et al. (2019) "A theory of instruction for introductory programming skills," *Computer Science Education* 29(2–3), DOI 10.1080/08993408.2019.1565235 (verified): sequences four skills — (1) **tracing** (reading code and predicting state changes and outputs), (2) writing correct syntax, (3) recognizing templates' parts and objectives, (4) using templates to solve problems. Core principle: learn to read before write, semantics before templates. Exploratory mixed-methods study: incremental skill teaching gave improved completion on practice exercises, lower error rate, better post-test understanding. Evidence is modest (exploratory, no independent replication found) — [PDF (UW)](https://faculty.washington.edu/ajko/papers/Xie2019IntroCSTheoryOfInstruction.pdf); [T&F](https://informahealthcare.com/doi/abs/10.1080/08993408.2019.1565235)
- [R] Related comprehension-first tutor PLTutor (Nelson, Xie, Ko, ICER 2017) compared against a writing-focused Codecademy tutorial in a small study — preliminary — [PDF](https://faculty.washington.edu/ajko/papers/Nelson2017PLTutor.pdf)
- [R] Lister et al. (2004) ITiCSE working group, "A multi-national study of reading and tracing skills in novice programmers," DOI 10.1145/1044550.1041673 — many students who had passed CS1 could not reliably trace short array code (older, 2004; not re-verified).
- [R] Lopez, Whalley, Robbins & Lister (2008, ICER) "Relationships between reading, tracing and writing skills in introductory programming," DOI 10.1145/1404520.1404535 — tracing and explaining-in-plain-English skill predict code-writing performance (older; not re-verified).
- [R] PRIMM (Predict–Run–Investigate–Modify–Make): Sentance, Waite & Kallia (2019) *Computer Science Education*, DOI 10.1080/08993408.2019.1608781 — structure that starts with *predicting* what given code does before running it (not re-verified). Note: studied mostly in school (age 11–14) contexts.

**Python-specific misconception inventory (progmiscon.org)**
- [R] Chiodini et al. (2021) "A Curated Inventory of Programming Language Misconceptions," ITiCSE 2021 — defines a PL misconception as a statement disprovable from the language's syntax/semantics alone; site progmiscon.org — [paper PDF](https://luce.si.usi.ch/assets/publications/chiodiniCuratedInventoryProgramming2021.pdf); a 2025 paper reports the site now holds 200+ misconceptions across languages — [Dagstuhl OASIcs 2025](https://drops.dagstuhl.de/storage/01oasics/oasics-vol134-programming2025/html/OASIcs.Programming.2025.21/OASIcs.Programming.2025.21.html)
- The Python section of progmiscon (fetched Nov 2026) lists **30** misconceptions — [progmiscon Python](https://progmiscon.org/misconceptions/Python/). The most relevant to this curriculum:
  - *AssignCompares* — believing `=` compares values.
  - *AssignmentCopiesObject* — believing assignment copies the object (→ list aliasing bugs).
  - *VariablesHoldObjects* — believing a variable contains a whole object (vs. a reference).
  - *VariablesHoldExpressions* — believing `=` stores an expression (so `a = b + 1` "updates" when b changes).
  - *ConditionalIsSequence* — believing `if/else` ≡ two sequential `if`s.
  - *IfIsLoop* — believing an `if` body repeats while the condition holds.
  - *ComparisonWithBoolLiteral*, *MapToBooleanWithIf* — writing `if x == True` / `if cond: return True else: return False`.
  - *NoShortCircuit* — believing `and`/`or` always evaluate both operands (matters for `if 0 <= r < R and grid[r][c]` bounds checks).
  - *DeferredReturn* — believing a mid-function `return` doesn't exit immediately.
  - *ReturnUnwindsMultipleFrames* — believing `return` can unwind several call frames (key recursion misconception).
  - *RecursiveFunctionNeedsIfElse* — believing a recursive function must contain if-else.
  - *OutsideInFunctionNesting*, *RightToLeftChaining* — wrong evaluation order for nested calls / chained accesses.
  - *MultipleValuesReturn* — believing functions return multiple values (Python actually returns one tuple).
  - *InitReturnsObject*, *InitCreates*, *NoEmptyInit*, *SelfAssignable* — class/`__init__`/`self` misconceptions.
  - *ParenthesesOnlyIfArgument* — believing `()` is optional for zero-arg calls (`lst.sort` vs `lst.sort()`).

**Python gotchas documented by the official docs [D]**
- Aliasing: "Why did changing list 'y' also change list 'x'?" — assignment never copies; `y = x` makes both names refer to the same list — [Python FAQ](https://docs.python.org/3/faq/programming.html#why-did-changing-list-y-also-change-list-x)
- Mutable default arguments: default values are evaluated once at definition time and shared across calls ("Why are default values shared between objects?") — [Python FAQ](https://docs.python.org/3/faq/programming.html#why-are-default-values-shared-between-objects)
- Scope: assigning to a name anywhere in a function makes it local, causing `UnboundLocalError` when read before assignment — [Python FAQ](https://docs.python.org/3/faq/programming.html#why-am-i-getting-an-unboundlocalerror-when-the-variable-has-a-value)
- Mutating while iterating: the tutorial warns that code modifying a collection while iterating over it "can be tricky to get right" and recommends iterating over a copy or building a new collection — [Python tutorial, for statements](https://docs.python.org/3/tutorial/controlflow.html#for-statements)
- `[[0]*m]*n` creates n references to the same inner list — [Python FAQ: How do I create a multidimensional list?](https://docs.python.org/3/faq/programming.html#how-do-i-create-a-multidimensional-list)
- Floor division `//` rounds toward negative infinity (so `-7 // 2 == -4`) and `/` always returns float in Python 3 — [Python reference, binary arithmetic](https://docs.python.org/3/reference/expressions.html#binary-arithmetic-operations)

**Classic (language-independent) variable/assignment misconceptions**
- [R] Kaczmarczyk et al. (2010, SIGCSE) "Identifying student misconceptions of programming," DOI 10.1145/1734263.1734299 — misconceptions about memory/references and assignment were among the most persistent (older; not re-verified).
- [R] An empirical study of student misconceptions with Python as the intro language exists at St Andrews ("Analysis of student misconceptions using Python as an introductory language") — [St Andrews portal](https://research-portal.st-andrews.ac.uk/en/publications/analysis-of-student-misconceptions-using-python-as-an-introductor/) (found via search; full text not read).

### Inferences
- **Make the notional machine the first-class "lesson object."** For every Python 0A module, the lesson should present a *memory diagram* (frames on the left, objects on the right, arrows = references) — essentially Python Tutor's visualization — and the practice set should begin with items where the learner *produces or selects* the diagram state, not just watches it (Sorva's "visual program simulation" + Hundhausen/Naps engagement findings in Q2).
- **Item-type ladder per concept (read → trace → modify → write):** (1) predict-the-output MCQ with distractors built from the progmiscon misconceptions above; (2) fill-in trace table (variable values per line/iteration); (3) "draw/choose the memory diagram after line k"; (4) find-and-fix bug; (5) Parsons; (6) write from scratch with tests. This aligns with Xie 2019 (trace before write) and PRIMM (predict before run).
- **Distractor engineering is the key leverage point:** each wrong MCQ option should map to exactly one named misconception (e.g., for `b = a; b.append(3); print(a)`, distractor "[1, 2]" = AssignmentCopiesObject). The platform can then diagnose which misconception a learner holds and route to a targeted micro-lesson.
- For a *rusty re-learner*, misconceptions about references/aliasing, mutable defaults, and floor division are more likely than first-week novice misconceptions (AssignCompares, IfIsLoop); a short diagnostic pre-test using predict-the-output items could let them skip mastered modules. (Inference; no study of re-learners specifically was found.)

### Gaps
- No study found that specifically measures misconceptions of *adult re-learners* (vs. first-time novices) in Python.
- No controlled effect sizes retrieved this session for Python Tutor's learning impact (Guo 2013 is primarily a tool/usage paper).
- Return-vs-print and off-by-one with `range` are widely reported by instructors but I did not retrieve a Python-specific empirical prevalence figure this session; progmiscon's Python list does not include an explicit "return vs print" entry.

## Q2. Algorithm patterns: pattern-based teaching, DP, recursion, invariants, complexity, and visualization effectiveness

### Takeaway
Research support for *pattern-based* instruction exists but is older and from CS1 ("algorithmic patterns" / schemas), not from interview prep; the NeetCode/AlgoMonster-style "pattern templates" are strong **practitioner consensus**, not experimentally validated. For DP, the best-structured framework is Demaine's SRTBOT (MIT 6.006, 2020), and a validated DP concept inventory (SIGCSE 2025) documents concrete misconceptions (recursion = DP, DP always min/max, always 2D, fixed fill order). For recursion, research consistently shows novices default to a "loop" model and need explicit call-tree/"copies" diagrams. For visualizations, the meta-analytic finding is robust: **what learners *do* with a visualization matters more than what it shows** — passive viewing of animations has weak effect.

### Cited Findings

**Pattern / schema-based instruction**
- [R] Pattern-Oriented Instruction (POI): Muller, Ginat & Haberman (2007) "Pattern-oriented instruction and its influence on problem decomposition and solution construction," ITiCSE 2007, DOI 10.1145/1268784.1268830 (older, 2007; verified) — algorithmic patterns = reusable abstractions of solutions to recurring algorithmic tasks (e.g., find max in a sequence); CS1 study comparing a group given problems organized by POI vs same problems without; authors conclude patterns as guides help students identify problem structure and construct solutions — [SpringerProfessional/ACM](https://www.springerprofessional.de/doi/10.1145/1268784.1268830); [bibtex](https://bibtex.github.io/ITiCSE-2007-MullerGH.html)
- [R] Muller, Haberman & Averbuch (2004, ITiCSE) — teacher workshop shifting teachers from syntax-focused to pattern/problem-solving teaching; teachers found the shift difficult (older) — [academia.edu](https://www.academia.edu/90826751/_An_almost_pedagogical_pattern_for_pattern_based_problem_solving_instruction)
- [R] Xie et al. 2019 (Q1) explicitly includes "recognizing templates" and "using templates" as distinct, sequenced skills after tracing — i.e., templates should be taught as named, explained objects, not just code to memorize — [PDF](https://faculty.washington.edu/ajko/papers/Xie2019IntroCSTheoryOfInstruction.pdf)
- [R] Soloway (1986) "Learning to program = learning to construct mechanisms and explanations," CACM 29(9), DOI 10.1145/6592.6594 — the original "programming plans" (goal/plan schemas) argument (older, 1986; not re-verified).
- [R] Subgoal labeling of worked examples (Morrison, Margulieux & Guzdial, ICER 2015, DOI 10.1145/2787622.2787733) — labeling the steps of a worked example with their purpose improved novice problem-solving performance (not re-verified). Relevant to presenting templates with labeled steps ("init window", "expand", "shrink while invalid", "record answer").
- [P] NeetCode roadmap organizes ~150/250 LeetCode problems into the exact categories in this curriculum — [neetcode.io/roadmap](https://neetcode.io/roadmap) (practitioner; not fetched).

**DP teaching frameworks and misconceptions**
- [P] MIT 6.006 Spring 2020 (Demaine, Ku, Solomon): DP is taught over four lectures starting from *recursive problem solving* (Fibonacci, DAG shortest paths, bowling). **SRTBOT** = **S**ubproblems, **R**elations (recurrence), **T**opological order, **B**ase cases, **O**riginal problem, **T**ime; memoization is the added ingredient turning a recursive SRTBOT algorithm into DP — [MIT OCW Lecture 15](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/resources/lecture-15-dynamic-programming-part-1-srtbot-fib-dags-bowling/); [transcript](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/5f5418aa88d83ce0d7186cfe71f5890b_TDo3r5M1LNo.srt) (verified). Later lectures recast Bellman-Ford, subset sum, etc. in SRTBOT.
  - Note: SRTBOT's "topological order" step is exactly the bridge from top-down memoization to bottom-up tabulation — the order in which a table must be filled is a topological order of the subproblem dependency DAG.
- [R] Zehra, Ramanathan, Zhang & Zingaro, "Student Misconceptions of Dynamic Programming," SIGCSE 2018, pp. 556–561 (verified) — single-university interview study — [dblp](https://dblp.dagstuhl.de/rec/conf/sigcse/ZehraRZZ18.html)
- [R] Shindler et al. (2022) replication, *Computer Science Education* 32(3):288–312, DOI 10.1080/08993408.2022.2079865 — misconceptions generalized to other universities/larger samples; students struggle with **technique selection** (recognizing DP applies), **recurrence building**, and **inefficient implementations** — [T&F](https://informahealthcare.com/doi/abs/10.1080/08993408.2022.2079865); [UCI seminar page](https://www.ics.uci.edu/~theory/269/220401.html)
- [R] Ferland et al. (2025) "Construction and Preliminary Validation of a Dynamic Programming Concept Inventory," SIGCSE TS 2025, DOI 10.1145/3641554.3701918 (verified) — summary of prior work: students "often fail to recognize that DP is the best solution," and when attempting DP "often fail to select the correct base case or determine the proper overlapping subproblems." Misconceptions with prevalence (UC Irvine / Utah State) — [arXiv 2411.14655](https://arxiv.org/html/2411.14655v1):
  - 2D DP table always filled top-left → bottom-right (12% / 14%)
  - DP always involves min/max (46% at USU on one item)
  - Recursion is the same as DP (7%/7% on one item; 16%/39% on others)
  - Greedy features mistakenly linked to DP (20% at USU)
  - Not knowing which subproblems to solve / ignoring specific subproblems (13% / 37%)
  - Every problem has an efficient DP solution (37% / 31% on one item)
  - DP requires tracking state to reconstruct the solution (7% / 30%)
  - DP always requires a 2D array (10% / 5%)
  - DP requires nested loops with the inner loop solving a recurrence (8% / 7%)
  - Recurrence construction was deliberately excluded (procedural skill). Psychometrics: Cronbach's α ≈ 0.76. (Paper reports 172 students but acknowledgements sum to 156 — minor internal inconsistency.)

**Recursion: mental models**
- [R] Kahney (1983) hypothesized experts hold a **copies model** (each call is a fresh instance with its own variables) while novices hold a **loop model**; Kurland & Pea (1985) found children's misguided "looping" interpretation of Logo recursion persisted even when contradicted by program behavior (older, 1983/1985) — [Kurland & Pea via academia.edu](https://www.academia.edu/307690/Childrens_Mental_Models_of_Recursive_LOGO_Programs)
- [R] Götschi, Sanders & Galpin (Wits University, 2003–2006): many students develop a viable copies model, others non-viable models; after teaching changes (more complex recursive algorithms introduced earlier), more students developed the copies model (2003–2005 cohorts); a "passive" model also emerged (older) — [Sanders, Galpin, Götschi "Mental models of recursion revisited" (ITiCSE 2006)](https://homepages.inf.ed.ac.uk/vgalpin1/pubs/SGG06.html)
- [R] George (2000, PPIG): many novices who showed a copies model *with* explicit diagrammatic traces failed without them → mental models are unstable and **graphical trace representations are a necessary retrieval aid** (older, 2000) — [PPIG 2000](https://ppig.org/papers/2000-ppig-12th-george/)
- [R] Brown University work evaluates an **algebraic substitution** notional machine (from *How to Design Programs*) as a mechanical, consistent way to trace recursion — [paper PDF](https://cs.brown.edu/people/sk/Publications/Papers/Published/tfk-eval-trace-rec-subst-nm/paper.pdf)
- [R] progmiscon Python: *ReturnUnwindsMultipleFrames*, *RecursiveFunctionNeedsIfElse*, *DeferredReturn* — [progmiscon Python](https://progmiscon.org/misconceptions/Python/)

**Invariants: two pointers / binary search**
- [P/R] Bentley's *Programming Pearls* (1986; older) reported that most professional programmers given time could not write a correct binary search, and advocated reasoning with loop invariants (not re-verified this session).
- [P] Joshua Bloch (Google, 2006): the textbook `mid = (low + high) / 2` overflows for large arrays in fixed-width languages — "Nearly All Binary Searches and Mergesorts are Broken" (older; not re-verified) — [Google Research blog](https://research.google/blog/extra-extra-read-all-about-it-nearly-all-binary-searches-and-mergesorts-are-broken/). (Irrelevant to Python ints, but a classic interview talking point.)
- [P] Interview-prep "binary search on a monotone predicate" (first-true / boundary) template is widely taught by AlgoMonster and similar (practitioner; not fetched) — [algo.monster templates](https://algo.monster/templates)

**Complexity analysis**
- [R] Gal-Ezer & Zur (2004) "The efficiency of algorithms—misconceptions," *Computers & Education* 42(3), DOI 10.1016/j.compedu.2003.07.004 — high-school students judged efficiency by superficial features (e.g., shorter program or fewer variables ⇒ more efficient) (older; not re-verified).
- [D] Python's TimeComplexity wiki page documents costs of list/dict/set/deque operations (e.g., `list.pop(0)` and `x in list` are O(n); `deque.popleft` O(1)) — [wiki.python.org/moin/TimeComplexity](https://wiki.python.org/moin/TimeComplexity) (not fetched; long-standing page).

**Algorithm visualization (VisuAlgo-style) effectiveness**
- [R] Hundhausen, Douglas & Stasko (2002) "A Meta-Study of Algorithm Visualization Effectiveness," *J. Visual Languages & Computing* 13(3):259–290 (older, 2002; verified): meta-study of 24 experimental studies; central finding — **how students use AV technology has a greater impact on effectiveness than what the AV shows them**; studies grounded in cognitive-constructivist theory (active engagement) had the best predictive success — [academia.edu](https://www.academia.edu/15636659/A_Meta_Study_of_Algorithm_Visualization_Effectiveness); [dblp bibtex](https://dblp1.uni-trier.de/rec/bibtex/journals/vlc/HundhausenDS02)
- [R] Naps et al. (2002) ITiCSE working group "Exploring the role of visualization and engagement in computer science education," ITiCSE-WGR '02 pp. 131–152, DOI 10.1145/960568.782998 (older; verified): **Engagement Taxonomy** — (1) no viewing, (2) viewing, (3) responding (answering questions about the visualization), (4) changing (modifying input/parameters), (5) constructing (building one's own visualization), (6) presenting; hypothesis grounded in Bloom: higher engagement → better learning — [NII CiNii](https://cir.nii.ac.jp/crid/1360574096426136704?lang=en); [Warwick PVW 2004 follow-up (Myller et al. extension)](https://www.dcs.warwick.ac.uk/pvw04/p16.pdf)
- [R] Urquiza-Fuentes & Velázquez-Iturbide (2009) "A survey of successful evaluations of program visualization and algorithm animation systems," ACM TOCE 9(2), DOI 10.1145/1538234.1538236 — successful evaluations overwhelmingly involved engagement beyond passive viewing (older; not re-verified).
- [P] VisuAlgo (NUS, Steven Halim) is a widely used interactive visualizer with built-in quiz ("e-Lecture"/training) modes — [visualgo.net](https://visualgo.net) (not fetched). I found **no controlled study of VisuAlgo's learning effect** in this session.

### Inferences
- **Teach patterns as named templates with labeled subgoals and an explicit invariant**, not as code to memorize. Each pattern lesson = (a) the problem *signal* that triggers it, (b) the invariant, (c) the template with subgoal labels, (d) 1 worked example traced step-by-step, (e) 1 counterexample where the pattern does *not* apply (e.g., sliding window fails with negative numbers → prefix sums + hashmap). This combines POI (Muller 2007), template skills (Xie 2019), and subgoal labeling (Morrison 2015).
- **Recursion:** always pair code with a *call tree / stack-of-frames* diagram (copies model); because George (2000) shows the model is unstable without diagrams, early recursion practice items should ask the learner to *fill in* the call tree or the return value at each node, then fade the diagram. Introduce "leap of faith" (trust the recursive call on a smaller input, reason only about combining) *after* the learner can trace 2–3 levels — tracing builds the copies model, leap of faith scales it to trees/backtracking. (Sequencing is an inference; "leap of faith" itself is practitioner language, not a researched intervention.)
- **DP order (inference from SRTBOT + DPCI misconceptions):** brute-force recursion → identify repeated subproblems (draw the call tree and circle repeats) → memoize (top-down) → SRTBOT write-up in words → derive the topological order → bottom-up table → space optimization. Teaching top-down first leverages the recursion module and directly attacks "recursion = DP" by showing the *difference* (memo). Explicitly include items that break "DP = min/max", "DP = 2D table", and "always fill top-left→bottom-right" (e.g., interval DP filled by length; a counting DP; a boolean DP).
- **Binary search / two pointers:** teach with a written invariant comment in the template (e.g., "all indices < lo are False; all ≥ hi are True") and practice items where the learner picks the loop condition and update rules that *preserve the stated invariant*; test on sizes 0, 1, 2 to expose infinite loops.
- **Visualizations:** use them at Naps levels 3–5 — "responding" (predict next state before revealing), "changing" (learner picks input that triggers a case), "constructing" (learner fills the DP table / draws the window positions) — never as a passive animation. This is the most evidence-backed design rule in this whole area.
- **Complexity:** teach by counting the dominant operation as a function of n, plus a "hidden cost" cheat sheet (`in list`, `pop(0)`, slicing, string `+=` in loop). Practice: classify-the-Big-O MCQ with distractors from "shorter code = faster", and "predict the runtime when n doubles" experiments.

### Gaps
- **No experimental evidence found** that interview-oriented pattern catalogs (NeetCode/AlgoMonster/Grokking) outperform other approaches for interview performance; this remains practitioner consensus.
- No controlled study found comparing **top-down-memo-first vs bottom-up-first** DP instruction.
- No empirical study found on teaching **loop invariants specifically for two-pointer/binary-search** in interview prep (Bentley/Gries tradition is older and mostly argumentative).
- No measured-effect study found for **VisuAlgo** specifically.
- Recent (2023–2026) research on LLM-era algorithm learning was out of scope and not searched.

## Q3. "Plan before code": problem-solving frameworks (Polya, UMPIRE, interview frameworks) and evidence they help

### Takeaway
There is **moderate research evidence** that *explicitly teaching a problem-solving process* (Loksa et al., CHI 2016) and *forcing problem comprehension before coding* (e.g., solving a test case by hand first — Prather et al., SIGCSE 2019) help novices; interview-specific acronyms (UMPIRE, CTCI's 7 steps) are **practitioner frameworks with no direct experimental validation**, but they operationalize the same research-backed stages.

### Cited Findings
- [R] Loksa, Ko, Jernigan, Oleson, Mendez & Burnett, "Programming, Problem Solving, and Self-Awareness: Effects of Explicit Guidance," CHI 2016, pp. 1449–1461 (verified): two 2-week web-dev camps, 48 high-school students; explicit instruction in problem-solving stages + prompts **increased productivity, independence, and programming self-efficacy** — [PDF (UW)](https://faculty.washington.edu/ajko/papers/Loksa2016ProgrammingProblemSolving.pdf); [dblp](https://dblp.org/rec/conf/chi/LoksaKJOMB16). The paper's stage model (from prior knowledge of the paper; not re-verified this session): reinterpret the problem prompt → search for analogous problems → search for solutions → evaluate a potential solution → implement → evaluate the implemented solution.
- [R] Loksa's dissertation, "Explicitly Training Metacognition and Self-Regulation for Computer Programming" (UW) extends this line — [UW ResearchWorks](https://digital.lib.washington.edu/researchworks/items/2c8e1804-c9fe-4dda-834d-23a1b07f2789/full)

### Inferences
- The research-backed core is **"Understand via a hand-worked example before coding"** (Prather 2019) + **explicit, named stages with self-monitoring prompts** (Loksa 2016). UMPIRE maps cleanly: U ≈ reinterpret prompt + hand-solve test case; M ≈ search for analogous problems (pattern recognition — the explicit link between interview prep and POI research); P ≈ evaluate potential solution; I/R/E ≈ implement and evaluate.
- Platform design implication: make the plan **a gated, structured artifact** for algorithm problems — (1) restate the problem + constraints; (2) hand-solve 1–2 examples incl. an edge case (input → output); (3) name the pattern (Match) and why; (4) state brute force + complexity; (5) state optimized approach + invariant/state definition; (6) pseudocode; then code; then (7) dry-run trace on the example; (8) state complexity. ## Q4. SQL: documented misconceptions and error types, evidence on teaching approaches, and exercise types

### Takeaway
SQL errors are well-catalogued: Taipalus et al. classify them as **syntax, semantic, logical, and complications**, and the robust finding is that **logical errors and complications persist** while syntax/semantic errors get fixed (because the DBMS flags them). Large-scale data (Ahadi et al.) shows the most common semantic mistake is **omission**, concentrated in queries needing JOIN, subquery, or GROUP BY. Miedema et al. (ICER 2021; Koli 2023) trace errors to four misconception sources — prior course knowledge, over-generalization, language-based confusion, and incomplete/incorrect mental models — with prevalence of individual misconceptions ranging from 1% to 52%. Teaching evidence is thinner: visual query representations (SQLVis, QueryVis) show promise; micro-Parsons for SQL has a CHI 2024 study; teaching the *logical processing order* is strong practitioner consensus backed by PostgreSQL's own documented evaluation order.

**PostgreSQL semantics that underlie the classic misconceptions [D]**
- Logical evaluation order — PostgreSQL's SELECT reference lists the processing steps: WITH → FROM (incl. joins) → WHERE → GROUP BY / HAVING → SELECT output expressions (incl. window functions) → DISTINCT → set ops (UNION…) → ORDER BY → LIMIT/OFFSET — [PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)
- Output-column aliases can be used in ORDER BY (and GROUP BY) but **not in WHERE or HAVING** — [PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)
- With GROUP BY or aggregates, SELECT may not reference ungrouped columns except inside aggregates or when functionally dependent on the grouping key (PostgreSQL errors; MySQL historically permitted it) — [PostgreSQL SELECT, GROUP BY clause](https://www.postgresql.org/docs/current/sql-select.html#SQL-GROUPBY)
- "The fundamental difference between WHERE and HAVING": WHERE selects input rows before groups/aggregates are computed; HAVING selects group rows after — [PostgreSQL tutorial: Aggregate Functions](https://www.postgresql.org/docs/current/tutorial-agg.html)
- `x = NULL` yields null, not true; use `IS NULL` / `IS DISTINCT FROM` — [PostgreSQL comparison functions](https://www.postgresql.org/docs/current/functions-comparison.html)
- `NOT IN` with a NULL in the list/subquery yields null (no rows) — PostgreSQL wiki explicitly advises "Don't use NOT IN" (use NOT EXISTS) — [PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This#Don.27t_use_NOT_IN); [subquery expressions](https://www.postgresql.org/docs/current/functions-subquery.html)
- A restriction in a LEFT JOIN's ON clause is processed *before* the join, while one in WHERE is processed *after* — so filtering the right table in WHERE removes the NULL-extended rows (effectively an inner join) — [PostgreSQL: Table Expressions](https://www.postgresql.org/docs/current/queries-table-expressions.html)
- Window functions "do not cause rows to become grouped into a single output row"; they're allowed only in SELECT list and ORDER BY, forbidden in WHERE/GROUP BY/HAVING because they logically execute after those clauses — [PostgreSQL tutorial: Window Functions](https://www.postgresql.org/docs/current/tutorial-window.html)
- Default window frame with ORDER BY is RANGE UNBOUNDED PRECEDING … CURRENT ROW, **including the current row's ORDER BY peers** (ties) — cause of "running total jumps on ties" and LAST_VALUE surprises — [PostgreSQL: Window Function Calls](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS)
- LIMIT without an ORDER BY that yields a unique order returns "an unpredictable subset" — [PostgreSQL: LIMIT and OFFSET](https://www.postgresql.org/docs/current/queries-limit.html)
- Integer division truncates toward zero (`SELECT 3/4` → 0) — a classic bug in rate/retention/funnel metrics — [PostgreSQL math functions](https://www.postgresql.org/docs/current/functions-math.html)
- Aggregate `FILTER (WHERE …)` clause (pivot/funnel conditional aggregation) — [PostgreSQL: Aggregate Expressions](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-AGGREGATES); ordered-set aggregate `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)` for median — [PostgreSQL aggregate functions](https://www.postgresql.org/docs/current/functions-aggregate.html)

(2022) ITiCSE working group "Parsons Problems and Beyond: Systematic Literature Review and Empirical Study Designs" — [Aalto PDF](https://acris.aalto.fi/ws/portalfiles/portal/131069230/Parsons_Problems_and_Beyond_-_Systematic_Literature_Review_and_Empirical_Study_Designs_.pdf); Ericson, Margulieux & Rick (2017, Koli Calling) "Solving Parsons problems versus fixing and writing code," DOI 10.1145/3141880.3141895 — Parsons took less time with comparable learning gains (not re-verified).

### Inferences
- **Core teaching spine = logical processing order + result-table visualization.** Because PostgreSQL itself defines the evaluation order (and the alias/window/HAVING rules follow from it), teaching "a query is a pipeline of table→table transformations" gives one mental model that explains most "language-based" and "mental-model" misconceptions (Miedema categories 3–4). Every lesson's worked example should show the **intermediate table after each clause** (FROM → WHERE → GROUP → HAVING → SELECT → ORDER/LIMIT).
- **Prioritize logical-error practice**: since syntax/semantic errors self-correct via DBMS feedback but logical errors persist (Taipalus 2019, persistent-errors study), the platform's highest-value items are ones where a query *runs* but is wrong: "this query runs — does it answer the question? If not, fix it," and "predict the result table / row count."
- **Use one consistent schema/dataset across all SQL modules** (e.g., `users`, `orders`, `order_items`, `products`, `events`, `sessions`), deliberately seeded with NULLs, ties, duplicate names, customers with zero orders, users with gaps in activity — so each misconception has a trap built into the data. (Practitioner/inference; Taipalus's exercise-design model argues for choosing practice data that exposes error types.)
- **Exercise mix per SQL module:** predict-result-table (incl. row count), write-query (auto-checked against expected result set), fix-the-query (logical-error focus), Parsons for SQL clauses (early modules), "explain this query in plain English" (Lopez/Lister-style), and "decompose into CTEs" for later modules (addresses "So many brackets!" complexity mismanagement).
- **Omission (Ahadi)** suggests a checklist prompt in the plan step: "Which tables? Join keys? Any grouping? Any filtering before vs after grouping? Ties? NULLs? Distinct users vs events?"

#### D. SQL (PostgreSQL)

| Module | Core mental model | Key misconceptions | Best teaching example | Item types |
|---|---|---|---|---|
| Single-table | A query is a pipeline of table→table steps in **logical order**: FROM → WHERE (row-by-row predicate) → SELECT (project) → ORDER BY → LIMIT | `= NULL` instead of `IS NULL` [D]; AND vs OR on one column across rows (e.g., `WHERE city='A' AND city='B'` returns nothing) (Taipalus examples); SELECT alias used in WHERE [D]; LIMIT without ORDER BY [D]; `'single'` = string vs `"double"` = identifier in PG (P) | `employees` table with some NULL `manager_id` and a tie in salary; show intermediate table after each clause | PRT, RC, FB, PZ (clause order), WR |
| Aggregation | GROUP BY partitions rows into buckets and **collapses each bucket to one row**; SELECT may only show grouping keys or aggregates; WHERE filters rows *before* grouping, HAVING filters groups *after* | Aggregate in WHERE; ungrouped column in SELECT (PG error) [D]; WHERE vs HAVING [D]; `COUNT(col)` skips NULLs vs `COUNT(*)`; AVG ignores NULLs (P) | Orders per customer: draw buckets of rows, then the collapsed result; same query with a WHERE filter vs a HAVING filter | PRT (draw the buckets), FB (move condition WHERE↔HAVING), EXP, WR |
| Joins | A join pairs **every** matching left row with **every** matching right row (filtered Cartesian product) — row counts multiply; LEFT JOIN keeps unmatched left rows with NULLs | Join as one-to-one "lookup" → fan-out double counting in SUM after joining (P); missing join condition → Cartesian product (Brass & Goldberg; Taipalus); right-table filter in WHERE turns LEFT into INNER [D]; omission of needed joins (Ahadi) | `customers` (one with 0 orders, one with 3) LEFT JOIN `orders`; compare `COUNT(*)` vs `COUNT(o.id)`; then SUM of item prices after joining `order_items` (fan-out) | RC (predict row count!), PRT, FB (ON vs WHERE), WR |
| Subqueries / CTEs | Subquery as scalar / list / table; correlated subquery conceptually re-evaluated per outer row; CTE = named intermediate table — build complex queries as a sequence of verified steps | `=` with multi-row subquery (P); `NOT IN` with NULLs returns nothing [D]; scoping in correlated subqueries (P); nested-bracket overload ("So many brackets!") | "Employees earning more than their department average" solved three ways: correlated subquery, CTE + join, window AVG | Decompose-into-CTEs item, rewrite-between-forms, PRT, FB (NOT IN → NOT EXISTS) |
| Window functions | Like GROUP BY that **does not collapse rows**: PARTITION BY = groups, ORDER BY = order within group, frame = which rows feed the computation; evaluated after WHERE/GROUP/HAVING, so filter on them via a CTE | Window function in WHERE [D]; expecting row count to change like GROUP BY [D]; default RANGE frame includes ties → running totals jump / LAST_VALUE surprises [D]; ROW_NUMBER vs RANK vs DENSE_RANK on ties (P) | Top-2 products per category: `ROW_NUMBER() OVER (PARTITION BY category ORDER BY sales DESC)` in a CTE, then `WHERE rn <= 2`; repeat with RANK to show tie behavior | PRT (fill the window column by hand), "pick the ranking function" MCQ, FB, WR |
| Analytics (retention, funnels, gaps-and-islands, median, pivot) | Compose primitives: cohort = `MIN(date)` per user; funnel/pivot = conditional aggregation (`COUNT(*) FILTER (WHERE …)`) [D]; gaps-and-islands = `date − ROW_NUMBER()` constant per island (P); median = `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)` [D] | Integer division in rates (`3/4 = 0`) [D]; counting events instead of distinct users (P); off-by-one day windows and timestamp vs date (P); denominators from the wrong population (P) | 7-day retention on one `events` table: CTE 1 cohort, CTE 2 activity on day 7, final rate with `::numeric` cast; check each CTE's intermediate output | Multi-step CTE build with checkpoint PRT after each step, FB (integer division / COUNT DISTINCT), open-ended interview-style WR |
