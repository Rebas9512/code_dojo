# 通用题单打底，签名题与新题型补缺

截至 2026 年 11 月，面向美国大厂的算法练习，覆盖最好的单一题单是 **NeetCode 250**。它有 250 题，NeetCode 150 和 Blind 75 都是它的子集。用 2026 年 10 月的公司标签数据计算，它覆盖 Google、Meta、Amazon、Microsoft、Bloomberg 近六个月前 50 道高频题的 **82–88%**。Grind 169 是 74–82%，Blind 75 和 Grind 75 只有 36–52%，LeetCode 75 仅 10–16%。SQL 方面唯一主流的官方题单是 **LeetCode SQL 50**，50 题全部免费、全部支持 PostgreSQL，但它几乎不练窗口函数、留存、连续区间、中位数这些数据岗高频考点。

按岗位看，SWE 和大厂 MLE 的编码轮仍以算法题为主。数据分析、数据科学、数据工程三类岗位的分水岭在 SQL，尤其是窗口函数。pandas 是 SQL 之外的备选语言，用 NumPy 手写 ML 主要出现在 AI 实验室和部分 MLE 面试。按公司看，各家近期高频题高度趋同于约 20 道通用经典题，公司差异集中在少数"签名题"。Meta、LinkedIn、Airbnb 的签名题大多不在任何主流题单里。

2025–2026 年的变化不是算法轮消失：受访的 52 位 FAANG 面试官里，没有一人说所在公司放弃了算法题。变化在于新增了"读代码、改代码、扩展代码"的 AI 辅助轮（Meta 从 2025 年 10 月起，Google 2026 年试点）和多级递进的 OA（CodeSignal ICF），题目也更多是改编题，追问更深。

对 code-dojo 的建议分四块：

- **Python 线：** 以 NeetCode 250 为骨架，按 18 个类别映射到现有 5 个阶段，Blind 75 和力扣 Hot 100 作为里程碑标记，再加一个"面试混合"阶段。
- **SQL 线：** SQL 50 撑起阶段 0–3，阶段 4–5 主要靠自写题和 AI 出题补齐。
- **公司标签：** 作为独立、带快照日期的元数据层，只存 slug 和排名，只在私有环境使用。
- **新题型：** 补上多级递进题、读码改码题、"AI 面试官追问"三种。

研究笔记目录里的 `lists.json` 是建库的机器可读起点。

## 一份 NeetCode 250 覆盖五大厂近半年高频题的 82–88%

2026 年 11 月仍在广泛使用的主流算法题单有 8 份。三份呈严格嵌套：**Blind 75 ⊂ NeetCode 150 ⊂ NeetCode 250**，另外 Grind 75 ⊂ Grind 169。NeetCode 250 是 2025–2026 年唯一重要的新题单。NeetCode 在 2024 年 12 月 29 日发布它，定位是"最适合零基础"：在 NC150 之上加了 100 题，其中 32 道 Easy，且没有一道是会员题 ([X 发布帖](https://x.com/neetcode1/status/1873322718013362516); [neetcode.io](https://neetcode.io/practice))。2025 年 3 月 NeetCode 本人建议，多数人先做 NC150，"更好是 NeetCode 250"，然后再从全集随机刷 ([X](https://x.com/neetcode1/status/1906204613583544625))。

Grind 75/169 的作者是 Blind 75 的作者 Yangshun Tay，但题单内容自 **2022 年 9 月**后就没再改过，它的价值在于每题的优先级、建议用时和按周混排的顺序 ([Grind 75 Changelog](https://www.techinterviewhandbook.org/grind75/changelog); [Grind 75 FAQ](https://www.techinterviewhandbook.org/grind75/faq))。LeetCode 官方有三份算法学习计划：LeetCode 75（0 道 Hard）、Top Interview 150、Top 100 Liked（即力扣中文站的"热题 100"，学习计划 slug 同为 `top-100-liked`），三份都没有会员题 ([LeetCode 75](https://leetcode.com/studyplan/leetcode-75/); [Top Interview 150](https://leetcode.com/studyplan/top-interview-150/); [Top 100 Liked](https://leetcode.com/studyplan/top-100-liked/))。

下表的覆盖率由研究团队计算，方法是把各题单与最常用的公开公司标签数据集（liquidslr，2026-10-21 快照）按 slug 匹配。"五家"指 Google、Meta、Amazon、Microsoft、Bloomberg；"并集 94 题"是这五家近六个月各自前 50 名合并后的 94 道不重复题 ([liquidslr 数据集](https://github.com/liquidslr/leetcode-company-wise-problems))。

| 题单 | 题数 | 易/中/难 | LeetCode 会员题 | 维护状态 | 五家近六个月前 50 覆盖 | 并集 94 题命中（每 100 题命中） |
|---|---|---|---|---|---|---|
| Blind 75 | 75 | 19/49/7 | 6 | 2018 年发布 | 40–48% | 31（41） |
| Grind 75 | 75 | 24/42/9 | 0 | 2022-09 后未更新 | 36–52% | 33（44） |
| LeetCode 75 | 75 | 22/53/0 | 0 | LeetCode 官方 | 10–16% | 17（23） |
| NeetCode 150 | 150 | 28/101/21 | 7 | 持续维护 | 60–70% | 50（33） |
| Top Interview 150 | 150 | 39/93/18 | 0 | LeetCode 官方 | 68–74% | 53（35） |
| Top 100 Liked（热题 100） | 100 | 20/68/12 | 0 | LeetCode 官方 | 60–74% | 52（**52**） |
| Grind 169 | 169 | 41/102/26 | 12 | 2022-09 后未更新 | 74–82% | 62（37） |
| NeetCode 250 | 250 | 60/155/35 | 7 | 2024-12 发布 | **82–88%** | **70**（28） |

这张表说明两件事。第一，**绝对覆盖看 NeetCode 250，单位效率看热题 100**：热题 100 每 100 题命中 52 道并集高频题，效率最高，但上限只有 55%。叠加题单的收益递减明显：NC250 ∪ Grind 169 共 297 题，命中 78/94；再并上 Top Interview 150 到 334 题，命中 81；8 份题单全部合并是 375 题，也只到 83。剩下的是各家公司的长尾。在五家中至少三家进入前 50 的 44 道"共识题"里，NC250 覆盖 39 道，8 份题单都没收录的只有 Max Consecutive Ones 一道 ([liquidslr 数据集](https://github.com/liquidslr/leetcode-company-wise-problems))。

第二，这些数字只衡量**原题照搬**的频率。如果按频率加权去算每家近六个月的完整清单（Google 一家就有 793 题），NC250 的覆盖率会降到 39–48%。2025 年 9 月 Blind 上也有多名用户反映题单原题出现得越来越少，改编题和新题更多 ([Teamblind](https://www.teamblind.com/post/starting-to-feel-like-lc-sets-dont-really-show-up-in-interviews-anymore-jynit841))。这批覆盖率是研究团队用众包数据自行计算的，没有找到独立的第三方分析。

不同备考时长对应的题单，2026 年的主流建议是一致的 ([AlgoMind, 2026-10-30](https://www.algomind.app/blog/blind-75-vs-neetcode-150-vs-grind-75-vs-striver-a2z/))：

| 备考时长 | 建议 |
|---|---|
| 不到一个月、基础在 | Blind 75，再用 NC150 补栈、堆、回溯 |
| 约两个月 | Grind 75 默认计划 |
| 两到三个月 | 按顺序做完 NC150 |
| 从零开始或半年以上 | NeetCode 250 或 Striver A2Z |

LeetCode 75 自成一派，75 题里有 37 道不在 NC250、Grind 169、Top Interview 150 的任何一份里。它适合当热身，不该算作面试覆盖。

## 数据岗的分水岭在 SQL 窗口函数，而 SQL 50 恰好缺这一块

各岗位编码轮考的东西差别很大，但可以归结为下表。表中除 Amazon 官网外，信息主要来自候选人报告和备考网站。

| 岗位 | 编码轮实际考什么 | 骨架题单 | 补充来源 |
|---|---|---|---|
| SWE | 数据结构与算法；实用设计类（LRU、限流器）；部分公司加读码改码的 AI 轮 | NeetCode 250（+ Grind 169 / Top Interview 150 多出的题） | 公司签名题、多级递进题 |
| 数据分析师（DA） | SQL 为主，限时、连接 + 窗口函数 + CTE；JD 要求 Python 时才考基础 pandas | SQL 50 | LeetCode 免费分析题、DataLemur |
| 数据科学家（产品分析） | SQL + 产品案例，45–60 分钟；可选 pandas | SQL 50 + Introduction to Pandas / 30 Days of Pandas | 留存、漏斗、实验类 SQL |
| 数据工程师（DE） | SQL 窗口函数和自连接 + 纯 Python 字典/集合/列表题；数据建模后在同一模型上连写多条 SQL | SQL 50 + NC250 前两阶段 | 建模 + 多查询综合题 |
| MLE / Applied Scientist | 大厂以 LeetCode 中等到难题为主；AI 实验室和部分 Google/Amazon 面试要求手写 ML | NeetCode 250 | 15–30 道 NumPy 手写 ML 题 |

这张表来自以下证据。Meta 数据工程师的 60 分钟技术筛选大致是 25 分钟 SQL 加 25 分钟 Python，候选人的评价是"不难但极度赶时间" ([Glassdoor Meta DE](https://www.glassdoor.com/Interview/Meta-Interview-E40772-RVW105025258.htm))。Meta 产品分析方向的数据科学家技术筛选在 CoderPad 上考 SQL 加产品案例，**接受任何主流 SQL 方言** ([DataLemur Meta DS 指南](https://datalemur.com/blog/meta-data-scientist-interview-guide))；有 Blind 用户补充，"如果选 Python，就得会 pandas" ([Blind](https://www.teamblind.com/post/facebook-data-scientist-analytics-live-coding-sbhz5cwn))。按岗位统计 SQL 的出现频率：Interview Query 汇总 2023 年 1 月到 2025 年 6 月的面经，SQL 出现在 **39.4%** 的数据工程师报告和 19.8% 的数据科学家报告里 ([Interview Query](https://www.interviewquery.com/p/data-interview-statistics-2026))；Dataford 统计的 SQL 题量是数据分析师 66、数据工程师 44、数据科学家 30 ([Dataford](https://dataford.io/blog/sql-interview-report-2026))。Meta MLE 的编码轮仍是 LRU 缓存、岛屿数量变体、字典树这类标准算法题 ([Glassdoor Meta MLE](https://www.glassdoor.com/Interview/Meta-Interview-E40772-RVW103151353.htm))。Amazon Applied Scientist 偶尔会要求手写 AUC 计算 ([Glassdoor Amazon AS](https://www.glassdoor.com/Interview/Amazon-Interview-E6036-RVW104768247.htm))。

SQL 考点方面，各来源一致把**连接和窗口函数**排在最前，后面依次是 GROUP BY/HAVING 与条件聚合、CTE 与子查询、日期处理、NULL 和重复值处理。KDnuggets 指出窗口函数是候选人最常栽的地方：函数名背下来了，却不理解窗口框架、分区和排序 ([KDnuggets](https://kdnuggets.com/most-candidates-fail-these-sql-concepts-in-data-interviews))。反复出现的业务题型有：分组 Top N、连续天数（gaps-and-islands）、留存与流失、漏斗转化、滚动平均、环比和同比、行列转换、中位数、自连接。

SQL 50 的 7 个分节里**没有窗口函数专节**，窗口类题目只有零散的 6 道左右（Consecutive Numbers、Game Play Analysis IV、Last Person to Fit in the Bus、Restaurant Growth、Department Top Three Salaries、Product Price at a Given Date）。LeetCode 上的中位数、行列转换、连续区间题（569、571、2252、2173、2701）几乎全是会员题，免费的只有 180 ([LeetCode SQL 50](https://leetcode.com/studyplan/top-sql-50/); [LeetCode 数据库题库](https://leetcode.com/problemset/database/))。

SQL 题源的取舍主要看免费程度、方言和公司标签：

- **LeetCode：** 数据库类共 323 题，其中 **105 道免费、218 道会员**。每一道免费题都提供 MySQL、SQL Server、PostgreSQL、Oracle、Pandas 五种语言。2025–2026 年它还在持续加免费的分析型题目，如 3497 订阅转化、3716 流失风险客户、3673 僵尸会话 ([LeetCode 数据库题库](https://leetcode.com/problemset/database/))。
- **DataLemur：** 公开目录有 106 题，其中 54 道 SQL，带 Amazon、Facebook、Google 等公司来源标签，编辑器默认 PostgreSQL 14 ([DataLemur](https://datalemur.com/questions))。
- **StrataScratch：** 有 1000 多道带公司标签的题，但只有 75 道左右免费 ([StrataScratch 定价](https://platform.stratascratch.com/pricing))。
- **pgexercises：** 唯一内容可合法复用的 PostgreSQL 原生题集，题目目录采用 CC BY-SA 3.0 许可 ([pgexercises LICENSE](https://github.com/AlisdairO/pgexercises/blob/master/questions/LICENSE))。

方言不是障碍。HackerRank 测评环境提供 PostgreSQL 14.3 ([HackerRank](https://candidatesupport.hackerrank.com/hc/en-us/articles/4402913877523-Execution-Environment))，CoderPad 支持 MySQL 和 PostgreSQL ([CoderPad](https://coderpad.io/resources/docs/interview/databases/))，所以**用 PostgreSQL 判题几乎不损失真实性**。

pandas 和 ML 两条支线都较小。pandas 有两份官方计划：Introduction to Pandas（15 题，全部 Easy）和 30 Days of Pandas（33 题，5 道会员题），后者有 16 题与 SQL 50 共用，因为 LeetCode 的数据库题本来就能用 pandas 作答 ([30 Days of Pandas](https://leetcode.com/studyplan/30-days-of-pandas/))。手写 ML 的事实标准是 Deep-ML，但它的开源题库采用"仅限教育用途、不可转让、禁止商用"的许可 ([Deep-ML LICENSE](https://github.com/Open-Deep-ML/DML-OpenProblem/blob/main/LICENSE))。真正能改编复用的是 MIT 许可的 TorchLeet，共 65 题 ([TorchLeet](https://github.com/Exorust/TorchLeet))。TensorGym 已经关站 ([tensorgym.com](https://tensorgym.com/))。被点名最多的手写题是 NumPy 版 attention、k-means 和 conv2d，出自 OpenAI MLE 的面试，不过这条信息来自备考厂商，没有引用 OpenAI 的原始来源 ([Interview Coder](https://www.interviewcoder.co/blog/openai-ml-engineer-interview))。

## 各家近期题目趋同，区分度藏在少数签名题里

### 数据本身的性质与噪声

公司高频题的唯一系统性来源是 LeetCode 会员的公司标签。它按"30 天 / 3 个月 / 6 个月 / 6 个月以上 / 全部"五个窗口展示题目，频率是每个文件内归一化到 0–100 的相对值，不是原始次数。两个公开镜像的结构完全一致，说明这就是 LeetCode 当前的分窗方式：liquidslr 是 2026-10-21 的快照，470 家公司；snehasishroy 是 2026-07-12 的快照，660 家公司 ([liquidslr](https://github.com/liquidslr/leetcode-company-wise-problems); [snehasishroy](https://github.com/snehasishroy/leetcode-companywise-interview-questions))。

用户在 leetcode.com 上看到的公司题数与镜像的"全部"文件基本吻合。六大公司误差在 1–2% 以内，比如 Amazon 用户看到 2013 题，镜像为 2015。TikTok、Nvidia 等误差可达约 10%，例如 TikTok 是 290 对 317。这说明镜像抓的就是同一份标签。

近期窗口的信号很弱。Two Sum 在五家公司的 3 个月和 6 个月榜单里都排第 1。Google 近六个月前 100 里混进了 SQL 题（1757、181）和 JavaScript 入门题（2667），显然不是 SWE 算法轮的真实题目。Meta 30 天窗口只有 27 题，Apple 只有 4 题 ([liquidslr Google](https://github.com/liquidslr/leetcode-company-wise-problems/tree/main/Google); [liquidslr Apple](https://github.com/liquidslr/leetcode-company-wise-problems/tree/main/Apple))。Blind 用户也抱怨同一时间窗内的排名自相矛盾，认为标签"永远不会完全准确，只是参考" ([Blind](https://www.teamblind.com/post/frequency-ranking-inconsistencies-on-leetcode-xneb0ktn); [Blind](https://www.teamblind.com/post/leetcode-company-tag-accuracy-lf5qiwak))。

### 签名题落在主流题单之外

公司差异在签名题上。本报告用 `lists.json` 核对了研究笔记列出的各家签名题，结果如下：

| 公司 | 核对的题（去掉 Two Sum 等通用题） | 在 NC250 中 | 8 份主流题单都没收录 |
|---|---|---|---|
| Meta | 全时段前 20 与 Meta 独有题，共 24 道 | 9 | **10** |
| LinkedIn | 6 道 | **0** | 5 |
| Airbnb | 9 道 | **0** | 6 |
| Google | 6 道独有题 | 2 | 4 |

Meta 漏掉的包括 1249、408、314、1650、339、1762、1570。数据集层面也能看到这一点：NC250 只覆盖 Meta 全时段前 100 的 **52%**，而 Amazon 是 82% ([liquidslr Meta](https://github.com/liquidslr/leetcode-company-wise-problems/blob/main/Meta/5.%20All.csv))。

反过来，跨公司反复出现的"实用设计"类题目都能在 **NC250 ∪ Grind 169 ∪ Top Interview 150** 里找到：146 LRU、460 LFU、981 时间键值存储、362 点击计数器、380 O(1) 插入删除随机、68 文本对齐。其中只有 3 道在 NC250 里。在笔记统计的 14 家非五大厂公司里，146 LRU 是 TikTok、Oracle、ByteDance 的第 1 名，出现在其中 12 家的标签里，10 家排进前 50 ([liquidslr 数据集](https://github.com/liquidslr/leetcode-company-wise-problems))。

### 按稳定度和体量决定练法

标签值不值得练取决于两个指标：题池大小，以及近期题落在全时段前 50 里的比例。按这两个指标，公司分成四类：

| 练法 | 公司 | 理由 |
|---|---|---|
| 整个标签刷完 | Pinterest、Airbnb、Snowflake | 题池分别为 41、62、100 题；近期题落在全时段前 50 的比例分别为 12/12、7/8、14/17，最稳定 |
| 全时段前 50 + 近六个月 | 五大厂、LinkedIn、Nvidia、Walmart、Uber | 题池大但头部稳定 |
| 只看近期窗口 | Infosys、Salesforce、TikTok、高盛、Visa | 近期题落在全时段前 50 的比例分别为 21%、27%、44%、49%、50%，题目轮换快 |
| 基本可以忽略 | Oracle、IBM | 头部几乎全是通用经典题 |

SQL 信号最强的是 IBM、Walmart、Infosys 和 Visa 数据岗。Snowflake 的 SWE 面试考的是数据库内核风味的算法与设计，它的 LeetCode 标签里没有一道数据库题 ([liquidslr 数据集](https://github.com/liquidslr/leetcode-company-wise-problems))。

## AI 轮考的是读码改码，OA 正在变成多级递进项目

### 算法轮还在，题目更难、更多改编

算法轮没有退场，而是变难、变"不像原题"。interviewing.io 在 2025 年调查了 67 位面试官，其中 52 位来自 FAANG。这 52 人里**没有一人**说公司放弃了算法题，58% 说换了题型，21% 承认故意出更难的题 ([interviewing.io](https://interviewing.io/blog/how-is-ai-changing-interview-processes-not-much-and-a-whole-lot))。The Pragmatic Engineer 的调查给出了各家的具体变化：Meta 出热门题的变体，Amazon 减少原样照搬的 LeetCode 题，Google 出用陌生术语包装的多段式题目，Microsoft 出改编题 ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/the-pulse-146))。

背后的原因是作弊太容易。interviewing.io 在约 2024 年做过一个小样本实验：偷用 ChatGPT 的候选人，原题通过率 73%，轻度改编题 67%，基线是 53%；只有完全自定义的题能挡住作弊 ([interviewing.io](https://interviewing.io/blog/how-hard-is-it-to-cheat-with-chatgpt-in-technical-interviews))。于是公司开始反作弊。Google CEO Pichai 表示至少恢复一轮线下面试 ([Axios](https://www.axios.com/2025/08/12/in-person-job-interview-artificial-intelligence))，面试官也普遍改用逐行追问"为什么这样写"、隔段时间重问同一问题、快问快答等手段。这些手段检验的都是能否当场流利地写出代码并讲清楚。**对选题的含义是：死记一份题单的价值在下降，同一套路的多个变体和讲清复杂度的能力在上升。**

### 新的 AI 轮考读码、改码、验证

新出现的 AI 轮考的不是"让 AI 写代码"，而是读码、改码和验证。

- **Meta：** 2025 年 10 月起，onsite 两轮编码之一换成 60 分钟的 CoderPad 轮。界面是文件树、编辑器、AI 对话三栏，AI 只能在对话框里回答，**所有代码由候选人自己敲**。题目在一个几百到几千行、不是候选人写的多文件代码库上分三段进行：先修 bug，再实现核心功能（难度"高于 LeetCode 中等题"），最后按分层测试数据做优化。哪些级别要考这一轮，各来源说法不一 ([Hello Interview](https://www.hellointerview.com/blog/meta-ai-enabled-coding); [interviewing.io Meta](https://interviewing.io/meta-interview-questions))。
- **Google：** 2026 年 5 月起试点用 Gemini 的"代码理解"轮，候选人阅读、调试、优化现有代码库，评估"AI 熟练度，包括提示工程、输出验证与调试"。10 月的报道称试点在扩大，Google 表示 AI 熟练度已是所有 SWE 职位的要求 ([Asia Economy](https://www.asiae.co.kr/en/article/2026050809233801400); [Tekedia](https://www.tekedia.com/google-expands-ai-powered-hiring-tests-making-ai-fluency-mandatory-for-software-engineers/))。这一轮是替换还是新增一轮传统编码，各来源说法矛盾。
- **其他公司：** LinkedIn 的 "coding with AI" 轮只有一份报告。Amazon OA 加入"AI 辅助的代码仓库题"一说也只见于一篇无法打开的帖子，均未证实 ([LC Discuss](https://leetcode.com/discuss/post/8444926/amazon-sde-online-assessment-2026-recent-etbq/))。
- **行业整体：** Karat 的调查显示 **62%** 的组织仍禁止技术面试中使用 AI ([Karat](https://karat.com/engineering-interview-trends-2026/))。

我找到的每个大厂面试流程里，AI 轮都与无 AI 的算法轮并存，没有一家用它替换全部算法轮。

### OA 平台：多级递进与"调试一个应用"

OA 平台的变化和面试一致。CodeSignal 的 **Industry Coding Framework（ICF）** 是一个项目分 4 级递进，每级加新方法和新实体 ([CodeSignal ICF 数据表](https://discover.codesignal.com/rs/659-AFH-023/images/CodeSignal-Industry-Coding-Framework-Datasheet.pdf))。eBay 和 Anthropic 的报告题目都是"内存数据库"：第 1 级增删改查，第 2 级前缀过滤，第 3 级 TTL，第 4 级历史回看或备份恢复 ([LC Discuss eBay](https://leetcode.com/discuss/post/7316549/ebay-codesignal-oa-industry-coding-asses-8qbn/))。OpenAI 和 Stripe 的实用编码轮也是同一路子：LRU 缓存、可恢复迭代器、时间键值存储、按 key 限流，先写基础版，再不断加需求 ([IGotAnOffer](https://igotanoffer.com/en/advice/openai-coding-interview))。

调试类和 AI 辅助类形式也在增加。高盛 OA 有调试现成应用的 "Software Diagnostics"，Walmart OA 有借 AI 助手的调试题，Airbnb 在 2024 年用代码评审轮替换了一轮编码。HackerRank 的 AI 面试官 Chakra 在 2026 年 10 月正式上线，题目基于真实代码仓库，并追问"为什么选这个方案、约束变了怎么改"，客户包括 Amazon、Nvidia、Snowflake ([TechCrunch](https://techcrunch.com/2026/10/05/hackerranks-ai-interviewer-offers-a-glimpse-into-what-job-interviews-could-become/))。CodeSignal 先后上线了 AI 辅助测评 Cosmo（2025 年 5 月）和允许使用 Claude Code、Cursor 的 Agentic 测评（2026 年 3 月）([CodeSignal](https://codesignal.com/newsroom/press-releases/codesignal-launches-ai-assisted-coding-assessments-and-interviews-redefining-technical-hiring-in-the-ai-era/))。

### 对选题的影响

落到选题上，影响有五点：

- **加重有状态的设计题：** 146、460、981、362、380、2043、588。
- **加入照规格实现的模拟题：** 68 文本对齐，以及 Visa 那类网格模拟。
- **按平台分开准备 OA：** CodeSignal 平台的公司（Uber、Visa）练 4 题 70 分钟的节奏，HackerRank 平台的公司练 2–3 题 90 分钟。
- **Amazon 补近期新题号：** Amazon 近期榜单里出现 3413、3914 这类新题号，与 OA 题被陆续收录进 LeetCode 的情况一致，所以要补近期新题号的中等题。
- **SQL 现场轮仍以无 AI 为主：** 已经有数据分析岗允许在 SQL 轮使用 AI，考察重心随之转向解释和验证结果 ([WSU](https://ascc.wsu.edu/blog/2026/07/15/data-analyst-interviews-are-changing-with-ai/))，但手写熟练度依旧是核心。

## code-dojo：两条骨架、一层公司元数据、三种新题型

### Python 线：NeetCode 250 做骨架，Blind 75 和热题 100 做里程碑

README 目前暂定 Python 线映射力扣热题 100。热题 100 单位效率最高，但对五大厂并集高频题的覆盖上限只有 55%，NeetCode 250 是 74%。另外 NC250 的 18 个类别顺序几乎与 code-dojo 现有的阶段一一对应，而且它是三层嵌套的超集，可以直接把 Blind 75 和 NC150 标成"核心"里程碑。

建议改为 **NeetCode 250 做骨架，热题 100 保留为里程碑标记**。热题 100 中有 83 道在 NC250 里，另外 17 道应该补进对应阶段，其中包括 Meta 全时段前 20 的 236（二叉树最近公共祖先），以及 Meta 近六个月前 20 的 31（下一个排列）和 283（移动零）。

| code-dojo 阶段 | NeetCode 250 类别（题数） | 合计 | 其中 NC150 / Blind 75 | 补充 |
|---|---|---|---|---|
| 0 语法热身 | 无 | 0 | — | 自写引导题；LeetCode 75 里 37 道独有的简单题（如 can-place-flowers、find-pivot-index）适合当热身 |

阶段 5 的设计依据是 Grind FAQ 的主张：混合主题的周计划更利于间隔重复，也更像真实面试中题目来自任何类别 ([Grind 75 FAQ](https://www.techinterviewhandbook.org/grind75/faq))。计时按实际面试设定：45 分钟面试槽里一道中等题约 20–25 分钟。

建库数据的来源与注意事项：

- **成员关系：** 用研究笔记目录里的 `lists.json`。它是 12 个键到 LeetCode slug 数组的映射，包括 Blind75、NC150、NC250、premiumAlgo100、Grind75、Grind169、leetcode-75、top-interview-150、top-100-liked、top-sql-50、30-days-of-pandas、introduction-to-pandas。数组**按字母排序，只表示成员关系**，不含顺序、分节、难度和会员标记。嵌套关系和各项交并集数量已与研究笔记核对一致。
- **类别：** 类别和顺序需要另外补。NC150 的类别可以从 MIT 许可的 neetcode-gh 仓库 `.problemSiteData.json` 取 ([neetcode-gh](https://github.com/neetcode-gh/leetcode))。NC250 多出的 100 题只存在于网站前端包里，没有许可声明，需要手工或让 AI 打类别标签。
- **premiumAlgo100：** 这个键是 NeetCode 代码里一个没有公开标签的会员题集合，100 题中 99 道是 LeetCode 会员题，不应作为骨架。
- **link 字段：** README 示例里的 `link` 指向 leetcode.cn。目标是美国公司，而公司数据集以 `leetcode.com/problems/<slug>` 为键，建议改指 leetcode.com。

### SQL 线：SQL 50 管阶段 0–3，阶段 4–5 要自己写

SQL 50 作为骨架没有争议：它是唯一的主流官方 SQL 题单，32 Easy / 17 Medium / 1 Hard，零会员题，全部可用 PostgreSQL 作答。但有两个问题要处理。

第一，**顺序不一致**。SQL 50 先讲连接、后讲聚合，code-dojo 是先聚合、后连接，而且 SQL 50 的分节名不代表题目实际用到的概念，例如"子查询"一节里的 Restaurant Growth 其实是滑动窗口题。建议按每道题**用到的最高概念**归入阶段，不照搬分节。

第二，**窗口函数和综合阶段几乎是空的**。按最高概念重排后的大致分布如下：

| code-dojo 阶段 | 可放入的 SQL 50 题（示例） | 约数 | 缺口与补充 |
|---|---|---|---|
| 0 单表查询 | 1757、584（NULL）、595、1148、1683、1667、1527、1517（正则）、196 | 9 | 足够 |
| 1 聚合 | 620、1211、1193（条件聚合）、2356、1141、596、1729、1484、610 | 9 | 足够 |
| 2 连接 | Basic Joins 全部 9 题（含 1581 反连接、197/1661 自连接、1280 交叉连接）、1731、1789、1251、1075、1327 | 14 | 足够 |
| 3 子查询和 CTE | 1978、626、1341、602、585、176、619、1045、1633、1174、1907 | 11 | 基本够，补相关子查询和 EXISTS |
| 4 窗口函数 | 180、550、1204、1321、185、1164、1070 | 7 | 明显不足：补免费题 177、178、184、601（连续区间），以及 DataLemur 的免费题 |
| 5 综合 | 几乎没有 | 0 | 留存、漏斗、连续登录、中位数、行列转换只能自写或 AI 出题；免费分析题 262、3497、3716、3657、3564、3673、3832 可作参照链接 |

阶段 4–5 正是 LeetCode 会员墙所在的地方，也正是 code-dojo 的"AI 当场出题 + 多数据集验证"最该发力的地方。AI 出题时可以按 README 已有的流程，强制生成并列、NULL、空分组等隐藏数据集。

其他配套建议：

- **MySQL 写法提示：** 网上参考解大量使用 MySQL，建议做一个提示，遇到 `DATE_ADD`、`IFNULL`、`LIMIT x,y`、`GROUP_CONCAT` 时给出 PostgreSQL 对应写法。
- **pgexercises：** 它的递归 CTE 和日期类题目可以按 CC BY-SA 3.0 改编引入，但要署名，并让衍生内容同样以 CC BY-SA 共享。
- **pandas 判题模式（后期）：** 只在目标是数据科学或数据分析岗时再加，题目夹具（建表脚本和数据）可以直接复用 SQL 题的，用服务端 Python 沙箱比对 DataFrame 结果。

### 公司标签：只存元数据、按快照版本化、按"提升度"排序

**数据源与数据模型。** 公司标签应当是独立于固定题库的一张表，不要写进 `problem.yaml`。字段为 `{company, window, rank, percentile, snapshot_date, source}`，以 leetcode.com slug 为键。两份数据源的分工如下：

| 数据源 | 快照 | 提供 | 缺陷 |
|---|---|---|---|
| liquidslr | 2026-10-21，470 家公司 | 频率与主题标签 | 没有题号，Acceptance 列是坏数据 |
| snehasishroy | 2026-07-12，660 家公司 | 题号 | 没有主题标签 |

两者按 URL slug 连接合并 ([liquidslr](https://github.com/liquidslr/leetcode-company-wise-problems); [snehasishroy](https://github.com/snehasishroy/leetcode-companywise-interview-questions))。

**时效。** 两个维护者每 1–3 个月刷新一次。"六个月"窗口是相对快照日期算的，所以 2026-10 快照覆盖的大约是 2026 年 4–10 月。liquidslr 的 README 仍写着"更新至 2025 年 6 月"，判断新旧要看提交日期，不要看说明文字 ([liquidslr 提交记录](https://github.com/liquidslr/leetcode-company-wise-problems/commits/main))。

**清洗与排序。**

- 频率是每个文件内归一化的相对值，要先转成名次或百分位才能跨窗口合并。
- 丢弃 30 天窗口，样本太小。
- SWE 标签里过滤掉 Database、JavaScript、Pandas 类题目（Google 的污染就在这里），但把 IBM、Walmart、Infosys、Uber 的 Database 题转给 SQL 线。
- 用"提升度"（该题在某公司的名次相对跨公司均值的偏离）把签名题顶到前面，否则每家的前 10 都是 Two Sum。

**公司视图怎么呈现。** 页面上只做三件事：显示骨架对该公司高频题的覆盖率；列出缺口题，例如"Meta 前 100 还差这些"；对缺口题中的会员题，让 AI 按同一算法思路出原创的同构题，并附原题链接作参考。

**许可与服务条款。** 这些限制决定了公司标签只能"私用、存元数据、不搬内容"：

- **LeetCode 服务条款：** 条款（2024-04-05 版）把题目和题解都声明为其版权内容，明确禁止爬取，禁止"直接与 LeetCode 竞争" ([LeetCode Terms](https://leetcode.com/terms/))。LeetCode 曾对泄露会员内容的仓库发过 DMCA 通知 ([GitHub DMCA 镜像](https://source-hub.etos-pro.ru/github/dmca/commit/a286358a334b6e1b5445f89a5ba21f2f34c3c813))。
- **数据集许可：** 两份新鲜数据集都**没有许可证**，制作过程本身就是用会员账号爬取。
- **不要自己写爬虫：** 用户本人有 LeetCode 账号，受条款约束，不应自己跑爬虫刷新数据。`lists.json` 也部分来自 LeetCode 的 GraphQL 接口和网站前端包，应当视为 2026-11-22 的一次性快照，不要做成定期回源 LeetCode 的流水线。
- **风险较低的做法：** 只存题号、slug、标题、公司、名次和外链。题面和测试按 README 的既定原则用自己的话重写。依据是美国版权法不保护思路和方法本身 ([17 U.S.C. §102(b)](https://www.law.cornell.edu/uscode/text/17/102))，"两数之和"这个任务本身不受保护，具体题面文字和测试数据受保护。
- **仓库保持私有：** 不在公开仓库或公开网站上发布公司清单。
- **题单许可：** Blind 75 和 NC150 的成员数据来自 MIT 许可的 neetcode-gh 仓库，最干净。NC250 没有许可声明；Grind 75 声明"保留所有权利"；Sean Prashad 的题单许可状态不明。个人自用风险很小，但这些数据都不应再分发。

README 已经定下的"单用户、登录墙后使用"与以上限制完全相容。以上是一般背景，不是法律意见。

### 新题型：多级递进、读码改码、面试官式追问

这三类形式是 2025–2026 年增长最快、而所有主流题单都没有的。

**多级递进题。** `problem.yaml` 需要支持 `levels`：每级有独立的需求说明和隐藏测试，做完一级才显示下一级，整题限时约 90 分钟。还需要"类模式"判题，用操作序列加参数数组驱动一个类。这个模式本来就是 LeetCode 设计题（146、460、981）的必需品，而 README 目前只有函数模式。题目种子可以取以下几类：

- 内存数据库：增删改查 → 前缀过滤 → TTL → 备份恢复
- LRU 扩展到 LFU
- 限流器：固定窗口 → 滑动窗口 → 按 key → 突发流量
- 时间键值存储
- 银行系统（2043）
- 文件系统（588）

另外可以记录前一级的代码在后一级被改写了多少，作为设计质量信号。

**读码改码题。** 给 2–5 个 Python 文件，内含一个植入的 bug 和一个失败的测试，要求先定位、解释、修复，再加一个功能。这对应 Meta AI 轮的第一、二阶段、Google 的代码理解轮、Airbnb 的代码评审和高盛的 Software Diagnostics。SQL 线可以做对应的"修这条查询"题，错误集中在 NULL、并列、重复值和 MySQL 专有写法上。

这类题可以复用 README 的验证机制：出题时 AI 已经要给"典型错误解法"，并保证每个错误解法至少挂一个测试。读码改码题只是把错误解法当作题面发给用户，同一套验证器原样可用。还可以专门生成"看起来像 AI 写的、带隐蔽 bug 的代码"，练习 Google 和 Canva 明确考察的"输出验证"能力。

**面试官式追问。** 提交通过后，AI 不只点评，还要扮演面试官：

- 要求用户写出复杂度和选这个数据结构的理由；
- 针对具体某行问"为什么"；
- 加一个变化，例如"输入改成流式""改成返回所有解"。

这一做法照搬了 HackerRank Chakra 和各家面试官现在的追问方式。对应地分两种模式。"AI 关闭"模式不给提示、不给自动补全、计时，模拟线下或监考场景；"AI 开启"模式允许问，但代码必须自己敲，并根据对话记录评估验证和理解程度。

**可选扩展。** 另外可以加两个模块：

- **OA 模拟：** CodeSignal 式 4 题 70 分钟，或 HackerRank 式 2–3 题 90 分钟。
- **NumPy 手写 ML 小线：** README "还可以做的"已列出。约 15–30 题，包括 k-means、kNN、线性/逻辑回归梯度下降、softmax 与交叉熵、AUC、注意力、层归一化、conv2d、MLP 反向传播。Deep-ML 只作标题和链接参考，TorchLeet 可以署名改编。这条线只在目标是 MLE 或 AI 实验室时值得做。

## 结论

这次调研最重要的结构性发现是：题库的三层"半衰期"差别很大，架构应当让它们彼此解耦。

- **套路层的半衰期按年计。** 2022 年后就没改过的 Grind 169 仍能覆盖五大厂近期高频题的 74–82%。
- **公司标签层的半衰期按月计。** 它每 1–3 个月刷新一次，噪声大，而且建立在无许可、违反服务条款爬取的数据上，随时可能消失。

所以 NeetCode 250 + SQL 50 的骨架必须能脱离公司数据独立运转，公司标签只作为可替换、可丢弃的排序和缺口提示层。公司标签真正有用的地方也不在"刷某公司前 50"，而在识别少数通用题单没覆盖的签名题和小而稳定的题池（Meta、LinkedIn、Airbnb、Pinterest、Snowflake），再用 AI 把其中的会员题转成原创同构题。

更深一层，2026 年题单与面试之间最大的错位不在选题，而在形式。多级递进、读码改码、追问变体这三种增长最快的形式，在任何主流题单里都不存在。公司为了防作弊而转向改编题和自定义题，恰好意味着"同一套路的新变体"才是最有价值的练习材料。code-dojo 已经设计好的"AI 出题 + 参考解 / 暴力解对拍 + 错误解必须被测试抓住"这套机制，正是批量生产这类材料所需的东西。SQL 线的缺口则集中在窗口函数和综合分析，恰好是 LeetCode 会员墙所在的位置。把 AI 出题的算力优先投向这两处，比再扩充任何一份现成题单收益更高。
