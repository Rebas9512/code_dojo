# 64b-tutor-memory-seamless：长期记忆改成后台自动、无感的设计（重写 docs/tutor-memory.md）

## 背景
64 交了第一版设计（`docs/tutor-memory.md`，运行记录在 `codex/runs/64-tutor-memory-design-*`）：显式"记住"指令、记忆页面、回执和撤销、清空批次、版本号。用户看完后改了方向：

> "记忆页面感觉不用记了 后台自动记就可以了，我想也不做成我指定去叫他记什么那种 就设计成一个比较seemless的那种自然记忆就可以"

用户以前也说过："反正就我自己用 把防御性的代码都撤掉"。这个应用也分发给少数其他人用，记忆只存在各自本机和各自的私有同步仓库里，只发给各自的 Claude / Codex 订阅。

**你只重写 `docs/tutor-memory.md`**，另外写 `{RUN_DIR}/report.md`。不改代码和测试。另一个任务 65 正在改 `desktop/`、`bootstrap/`、`deploy/README.md`、`docs/README.md`，不要碰这些文件。

## 新方向（主控整理）
- **没有记忆页面，没有"记住 / 忘掉"指令，回复下面也不显示"已记下"。** 学生不用管理记忆，助教自己观察、自己记，回答时自然用上。
- **从哪里学**：不只聊天，还有做题证据，比如正式提交的错误（含具名误解编号）、用了提示和看了题解、哪类题反复卡住、写法习惯。这些数据大多已经在同步的表里。
- **怎么写**：倾向于**后台整理**，不在每次聊天回复里顺带写。理由：不拖慢助教回复，不让每次调用都背着记忆写入的 schema，还能看到没有聊天的做题证据。请设计触发时机（比如一段练习结束、退出应用、每天第一次打开，有新证据才跑）、每次读多少证据、用哪个助教、用什么 effort、怎么避免重复处理同一批证据，以及一天大概跑几次、每次大概多少字。AI 关闭或命令找不到时就不跑。如果你读完代码认为"聊天回复顺带写"整体更好，可以推荐，但要把两种方案的代价列清楚。
- **记成什么样**：一份短小的"关于这位学生"笔记，按分类组织（常错点、学习状况、写法和讲解偏好、目标和背景），总长有上限。进度数字仍由数据库现算，不写进记忆。整理时可以合并、改写、删掉过时的内容，相当于每次重写或增量修改这份笔记。
- **怎么存、怎么同步**：选最简单、又不会明显丢东西的做法。读 `events.py` / `sync.py` 的实际行为来论证。可以利用一个事实：原始证据（聊天、提交）本身是同步的，换台机器后整理任务也能看到另一台的证据。两台机器离线各整理一次，后同步的覆盖先同步的，可以接受吗？会丢什么？怎么用"已处理到哪"的记号让丢的内容下次补回来？旧客户端遇到不认识的新表或新事件会怎样，也要写清楚。
- **怎么用**：注入助教提示词（放什么、按当前题挑哪些、上限多少）。附加题出题要不要参考常错点，给出推荐。复习排期不改（沿用 64 的结论）。学生问"你记得我什么"时，助教可以照实说。
- **控制**：不做页面，但建议保留一个最小的开关和"清空记忆"，放在现有的设置里（桌面版的设置窗口，以及浏览器版对应的位置）。默认开还是默认关，给出推荐和理由；用户倾向"无感"。
- **砍掉 64 里的重型机制**：清空批次、每条的版本号、回执和撤销、凭据正则拦截、两道题的证据门槛这些，除非确实必要，都不要。必要的写一句理由。不想记的内容（密码、联系方式、健康身份信息、一次性手误）靠提示词约束即可。

## 文档要回答的问题
1. 这份记忆是什么、从哪些证据来、写成什么样（给一个 10 行左右的样例笔记）。
2. 后台整理：触发、输入、输出 schema（兼顾 Claude `--json-schema` 和 Codex 严格 schema）、提示词要点、频率和用量估算。
3. 存储和同步：表或设置项怎么设计，和事件日志怎么接，跨机器的结果，旧客户端兼容。
4. 读：注入助教提示词的位置和上限；附加题要不要用。
5. 开关和清空。
6. 分期和派工：每期要改的文件、测试、估算（一个 codex 任务 15–30 分钟）。尽量一到两期做完。
7. 需要用户决定的事（每条给推荐的默认值），尽量少。

## 写法
- 中文，写"会是什么样"。控制在约 150 行以内，比 64 的版本短。
- 涉及现有代码的地方写清文件和函数名；不要虚构接口，拿不准的标"待确认"。
- 64 里仍然成立的结论（比如事件合并规则的分析）可以压缩后沿用。
