## 用户说的"开发目录下的 memory 功能"是什么
主控（Claude Code）在这个开发目录里有一套自动记忆，规则大致如下，记忆功能照这个模型设计：
- **一条记忆记一件事**。每条有：`name`（短 slug）、`description`（一句话摘要，用来判断这条和当前任务相关不相关）、`type`（类型）、正文。行为类的记忆在正文里附"为什么"和"怎么用"。
- **索引常驻**。所有记忆的 name + description 组成一份索引，每次对话开头都在上下文里；正文在相关时才看。
- **代理自己决定记什么**，不需要用户下指令。工作中了解到一件以后用得上、不明显的事，就记下来。先查有没有已经覆盖这件事的记忆，有就更新，不重复建。发现某条记忆错了或过时了，就删掉。
- **不记别处已经有的东西**：代码、git 历史能查到的不记。放到这里，就是数据库能算出来的通过率、用时、次数、到期复习都不记，只记数据库看不出来的定性判断。
- 相对日期一律写成绝对日期；记忆是某个时间点的判断，用之前要和最新情况核对。
- 记忆没有专门的管理界面；用户问起时，代理能说出自己记了什么。

## 映射到 code-dojo（主控的建议，你读完代码后可以调整，标"推断"）
- **类型**：
  - `learner`：关于学习者本人，比如目标、背景、每天能投入的时间。
  - `feedback`：学习者希望怎么被教、对助教的纠正，比如"先给小例子""别一次讲太多"。正文附为什么和怎么用。
  - `progress`：**助教自己维护的学习状况笔记**，比如现在的重点、哪些技能还不稳、反复出现的常错点（能对上 `docs/teaching-design.md` 的具名误解编号就带上）、下一步建议练什么，都写日期。用户说的"让 agent 自己管理我的学习进度"主要落在这一类。它是数据库排期之外的定性判断，不替代 `mastery` 的掌握度和复习排期。
- **存储**：一条记忆一行，按行同步，两台机器各写不同的记忆时都能保留。索引不单独存，从各行的 name 和 description 生成。合并语义要基于 `events.py` / `sync.py` 的实际行为来写：同一条被两边改时谁赢、删除会不会被旧改动带回来。64 里关于事件合并的分析可以压缩后沿用。
- **读**：助教是单次调用、没有工具（`claude -p --tools ""` / `codex exec`），没法像主控那样按需打开文件。所以由后端组装：索引全量放进提示词，再按当前题的线和技能挑出相关记忆的正文，或者干脆规定正文很短、全部放进去，你权衡后给出推荐，写清字数上限。学生问"你记得我什么"时照实说。
- **写**：两个时机，都由助教自己判断要不要动，界面上什么都不显示。
  1. **聊天时**：助教回复的结构化输出加一个 `memory` 字段（保存 / 更新 / 删除，按 name），通常为空。schema 要兼顾 Claude 的 `--json-schema` 和 Codex 的严格 schema（`codex_schema.strict_schema`）。
  2. **后台学习回顾**：很多时候学生只做题不聊天，`progress` 类记忆要靠做题证据更新，比如正式提交的对错和误解编号、提示和题解的使用、反复卡住的题。设计触发时机（比如一组练习结束、退出应用、每天第一次打开，有新证据才跑）、"已处理到哪"的记号、每次读多少证据、用哪个助教和 effort、一天大概跑几次、每次大概多少字。AI 关闭或命令找不到时就不跑。可以参考 `extra.py` 的后台线程做法。
- **提示词要点**：仿照上面的规则，写给助教的"什么时候记、怎么记"。也要写什么不记：密码、联系方式、健康身份信息、一次性手误、数据库已有的数字。
- **控制**：没有页面。只在现有设置里放一个开关和"清空记忆"（桌面版设置窗口，以及浏览器版对应的位置）。用户想要"无感"，推荐默认开，除非你发现有必须默认关的理由。
- **砍掉 64 里的重型机制**：清空批次、每条版本号、回执和撤销、凭据正则拦截、两道题的证据门槛、记忆页面，这次都不要。必要的保留项写一句理由。

## 文档要回答的问题
1. 这份记忆是什么，三类各给 2–3 条样例（写成实际会存的样子），再给一份生成出来的索引样例。
2. 读：注入助教提示词的位置、内容、上限；附加题出题要不要参考 `progress` 里的常错点，给推荐。复习排期不改。
3. 写：聊天时的 `memory` 字段（完整 schema）和后台学习回顾（触发、输入、输出、提示词要点、用量估算）。两条写入路径同时改同一条记忆时怎么办。
4. 存储和同步：表结构、和事件日志怎么接、跨机器结果、旧客户端遇到新表或新事件会怎样。
5. 开关和清空。
6. 分期和派工：每期要改的文件、测试、估算（一个 codex 任务 15–30 分钟）。尽量一到两期做完。
7. 需要用户决定的事（每条给推荐默认值），尽量少。

- 涉及现有代码的地方写清文件和函数名；不要虚构接口，拿不准的标"待确认"。
